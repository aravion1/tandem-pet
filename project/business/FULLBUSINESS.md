# Техническое задание: платформа управления коммуникациями коттеджного посёлка

## 1. Назначение и границы MVP

### 1.1. Цель

Создать mobile-first веб-платформу для коммуникации жителей коммерческого коттеджного посёлка с правлением: обработки обращений и задач, обсуждений, публикации новостей и постоянной справочной информации, а также контроля результатов работы правления.

### 1.2. Пользовательский результат

Житель получает единое защищённое пространство, где может направить обращение, участвовать в обсуждениях, читать актуальные новости и инфо-борды. Правление получает инструменты для обработки запросов, постановки задач, публикаций и анализа выполненной работы.

### 1.3. Входит в MVP

- обращения и связанные с ними задачи;
- публичные и приватные обсуждения;
- новости;
- инфо-борды;
- базовая аналитика по обращениям и задачам;
- учёт времени и бюджета по задачам;
- экспорт аналитики в Excel;
- гибкая система ролей и прав;
- уведомления через push, Telegram и MAX через заменяемые интеграционные интерфейсы;
- первичная авторизация по SMS и управление согласием на обработку персональных данных.

### 1.4. Не входит в MVP

- интеграция с 1С;
- автоматический учёт времени и бюджета из внешних систем;
- иные интеграции, кроме интерфейсов для SMS и мессенджеров.

## 2. Роли, участки и права доступа

### 2.1. Пользователи и участки

Все учётные записи принадлежат жителям посёлка. Один пользователь может быть связан с несколькими участками; один участок может иметь нескольких владельцев. Участок хранит как минимум улицу и номер дома. Связь пользователей и участков — многие-ко-многим.

### 2.2. Гибкие роли

Роль — именованный набор прав. Председатель правления создаёт роли и назначает им права. Базовые роли «житель», «правление», «бухгалтер», «председатель правления» и «заместитель председателя правления» являются преднастроенными наборами и могут быть изменены через систему прав.

Право `roles.manage` должно быть назначено председателю по умолчанию. Только обладатель этого права может создавать роли и назначать права.

### 2.3. Каталог прав MVP

| Право | Действие |
|---|---|
| `users.manage` | Импорт жителей, изменение номера телефона, назначение ролей и прав. |
| `requests.view_public` | Просмотр публичных обращений. |
| `requests.view_private` | Просмотр личных обращений, адресованных пользователю. |
| `requests.moderate` | Модерация обращений и смена их статуса. |
| `tasks.view` | Просмотр задач. |
| `tasks.manage` | Создание, изменение параметров и статусов задач. |
| `tasks.assign` | Назначение исполнителей задач. |
| `tasks.close` | Финальное подтверждение выполнения задачи. |
| `discussions.moderate` | Назначение вердикта и закрытие обсуждения. |
| `news.manage` | Создание, изменение, публикация и снятие с публикации новостей. |
| `infoboards.manage` | Создание, изменение, публикация и снятие с публикации инфо-бордов. |
| `analytics.view` | Просмотр аналитики. |
| `analytics.export` | Выгрузка аналитики в Excel. |
| `budget.view` | Просмотр времени и бюджета задач. |
| `budget.manage` | Внесение и изменение времени и бюджета задач. |
| `audit.view` | Просмотр журнала действий и согласий. |
| `roles.manage` | Создание ролей и назначение прав. |

Доступ к каждому модулю и защищённому действию должен проверяться по соответствующему праву на сервере. Интерфейс не должен показывать недоступные действия.

## 3. Авторизация и персональные данные

### 3.1. Создание и активация учётных записей

1. Пользователь с правом `users.manage` импортирует список жителей: номер телефона, улицу и дом.
2. Самостоятельная регистрация не допускается: войти может только пользователь, чей номер есть в импортированном списке.
3. При первом входе пользователь подтверждает номер кодом SMS, задаёт пароль и подтверждает согласие на обработку персональных данных.
4. В последующих входах используются номер телефона и пароль. SMS отправляется только при первом входе и при восстановлении пароля.
5. Пароли хранятся только в виде криптографического хеша. Правление не имеет доступа к ним.
6. Номер телефона хранится в зашифрованном виде, поскольку он нужен для SMS и доступен только пользователям с соответствующим правом. Хеш может использоваться как дополнительный индекс поиска, но не заменяет зашифрованный номер.
7. По запросу жителя пользователь с правом `users.manage` может изменить номер телефона учётной записи. Это действие фиксируется в аудите.

### 3.2. Согласия и аудит

Система должна фиксировать факт, дату и версию текста согласия на обработку ПДн. До подтверждения согласия доступ к функциям пользователя ограничен процессом активации. Все действия, влияющие на права, телефоны, статусы, бюджет, публикации и согласия, должны сохраняться в неизменяемом журнале аудита с автором и временем.

### 3.3. Требование соответствия

Хранение и обработка персональных данных должны соответствовать применимым требованиям законодательства Российской Федерации. Конкретные организационные и технические меры подлежат отдельному юридическому и информационно-безопасностному согласованию до ввода системы в эксплуатацию.

## 4. Функциональные требования

### 4.1. Обращения

Житель создаёт обращение с темой, описанием, приоритетом и вложениями. При создании он выбирает видимость:

- **публичное** — доступно всем пользователям с правом `requests.view_public`; модерировать может любой пользователь с `requests.moderate`;
- **личное** — адресовано выбранному члену правления; доступно автору, адресату и пользователям с `requests.view_private`.

Обращение поддерживает комментарии, вложения, приоритет, историю изменений и уведомления. Начальный статус — «В очереди».

Статусы обращения:

| Статус | Значение |
|---|---|
| В очереди | Обращение создано и ожидает обработки. |
| В работе | Член правления начал обработку. После перехода житель не может отменить обращение. |
| Выполнено | Результат подтверждён модератором. |
| Отменено | Житель отменил обращение до начала работы. |
| Отказано | Модератор дал отрицательный ответ. |

Каждое изменение статуса, исполнителя, приоритета, видимости или содержания фиксируется в истории.

### 4.2. Задачи

Задача предназначена для работ, требующих фактического выполнения. Она содержит тему, описание, приоритет, исполнителя или исполнителей, срок, вложения, комментарии, фактически затраченное время и бюджет.

Задача создаётся отдельно либо преобразованием обращения. При преобразовании тип исходной сущности меняется на «задача», а полная история обращения сохраняется. Между историческими записями должна оставаться ссылка на исходное обращение.

Статусы задачи:

| Статус | Значение |
|---|---|
| В очереди | Создана и ожидает начала работ. |
| В работе | Работы выполняются. |
| Приостановлено | Выполнение временно невозможно или ожидает внешних действий. |
| На проверке | Исполнитель сообщил о завершении и ожидает проверки. |
| Выполнено | Результат проверен и подтверждён только пользователем с `tasks.close`. |
| Отменено | Задача отменена уполномоченным пользователем. |

Переходы статусов, назначение исполнителей, сроки, приоритеты, время и бюджет должны вести историю. Задача может быть преобразована обратно в обращение с сохранением полной истории изменений.

### 4.3. Обсуждения

Обсуждение — отдельный чат с темой, участниками, сообщениями, вложениями и статусом. Любой пользователь может создавать публичное или приватное обсуждение:

- **публичное** — доступно всем пользователям;
- **приватное** — доступно только приглашённым участникам. Правление не имеет особого доступа к нему и видит его лишь при приглашении.

Автор приватного обсуждения приглашает участников. Автор любого обсуждения может закрыть его. Закрытое обсуждение и вся переписка сохраняются для участников, но отправка новых сообщений запрещается.

Участники могут поставить реакцию «лайк» на сообщение. Член правления, участвующий в обсуждении, при наличии `discussions.moderate` может пометить любое сообщение как вердикт и закрыть обсуждение. В обсуждении допускается один актуальный вердикт; его смена должна фиксироваться в истории.

### 4.4. Новости

Пользователь с `news.manage` создаёт, редактирует, публикует и снимает с публикации новости. Новость содержит заголовок, текст, вложения при необходимости, автора, дату создания и дату публикации. Публикация и изменения должны фиксироваться в аудите; жителям направляется уведомление о публикации.

### 4.5. Инфо-борды

Инфо-борд — доска, страница или баннер с редко изменяемой, но постоянно востребованной жителями информацией. Пользователь с `infoboards.manage` создаёт, редактирует, публикует и снимает его с публикации. Инфо-борд содержит заголовок, содержание, формат представления, вложения при необходимости, автора и дату последнего обновления.

### 4.6. Аналитика и экспорт

Пользователи с `analytics.view` получают аналитику за выбранный период:

- количество обращений по статусам;
- количество задач по статусам;
- количество выполненных задач;
- количество обработанных обращений;
- суммарное и деталированное время по задачам;
- суммарный и деталированный бюджет по задачам.

Пользователь с `analytics.export` может выгрузить эти данные в файл Excel. Финансовые показатели дополнительно защищаются правом `budget.view`.

### 4.7. Уведомления

Система должна создавать уведомления о следующих событиях: смена статуса обращения или задачи, новый комментарий, назначение исполнителя, публикация новости или инфо-борда, приглашение в обсуждение.

Уведомление отправляется во все доступные пользователю каналы: push, Telegram и MAX. Для SMS, Telegram и MAX требуется интеграционный интерфейс, чтобы конкретного поставщика можно было подключить или заменить без изменения бизнес-логики. SMS обязательно используется для первого входа и восстановления пароля.

## 5. Модель данных

Основные сущности: пользователь, роль, право, пользовательская роль, участок, связь пользователь–участок, обращение, задача, комментарий, вложение, история изменений, обсуждение, участник обсуждения, сообщение, реакция, вердикт, новость, инфо-борд, уведомление, запись времени, запись бюджета, согласие на обработку ПДн, запись аудита.

Ключевые связи:

- пользователь ↔ участок: многие-ко-многим;
- роль ↔ право: многие-ко-многим;
- пользователь ↔ роль: многие-ко-многим;
- обращение/задача → комментарии, вложения, история: один-ко-многим;
- обсуждение ↔ участник: многие-ко-многим;
- обсуждение → сообщения → реакции: один-ко-многим;
- задача → время и бюджет: один-ко-многим.

## 6. Технические и нефункциональные требования

- Архитектура: монолитное приложение в Docker-контейнерах.
- Backend API: PHP Laravel.
- Frontend: Vue 3.
- База данных: PostgreSQL.
- Кэш и фоновые механизмы: Redis.
- Интерфейс должен быть mobile-first и работать на мобильных устройствах, планшетах и настольных компьютерах в актуальных браузерах.
- Серверная часть обязана проверять аутентификацию, права доступа и область видимости данных для каждого запроса.
- Персональные данные, секреты интеграций и резервные копии должны быть защищены. Нужны резервное копирование и возможность восстановления данных.
- Решение должно иметь автоматизированные тесты; для приёмки MVP все автотесты должны успешно проходить.

## 7. Критерии приёмки MVP

MVP принимается, если:

1. Реализованы все функции раздела 4 и права из раздела 2.
2. Пользователь из импортированного списка проходит активацию по SMS, задаёт пароль и даёт согласие; пользователь вне списка войти не может.
3. Личные обращения не доступны посторонним пользователям, а приватные обсуждения не доступны правлению без приглашения.
4. Для обращений и задач доступны утверждённые статусы, а их история сохраняется при любом преобразовании типа сущности.
5. Только пользователь с `tasks.close` может завершить задачу статусом «Выполнено».
6. Права ограничивают как элементы интерфейса, так и серверные операции.
7. Аналитика рассчитывает утверждённые показатели за период, а экспорт формирует Excel-файл.
8. Уведомления создаются для всех перечисленных событий и используют доступные подключённые каналы.
9. Аудит фиксирует критические действия и согласия на обработку ПДн.
10. Все автоматизированные тесты успешно проходят, критические и блокирующие дефекты отсутствуют.

## 8. Риски и открытые вопросы

### Подтверждённые допущения

- Конкретные поставщики SMS, Telegram и MAX на этапе MVP не выбраны; реализуются интерфейсы интеграций и подключение выбранных провайдеров.
- Интеграция с 1С не входит в MVP.
- Расширенная аналитика, кроме утверждённых показателей, не входит в MVP.

### Открытые вопросы, не блокирующие старт проектирования

- Правила назначения исполнителей: могут ли ими быть только члены правления или также жители/внешние подрядчики. Ответ: Могут, в окне выбора исполнителя - можно выбрать либо из списка, либо ввести вручную ФИО/Организацию
- Форматы, предельный размер и правила проверки вложений. - Ответ: Любых размеров любой формат.
- Требуется ли редактирование/удаление жителем своих сообщений, обращений и обсуждений после публикации. - Ответ: нельзя редактировать.
- Конкретные SLA, требования к нагрузке, доступности и срокам хранения данных: Таких требований нет.
- Точный состав организационных и технических мер для соблюдения требований к ПДн должен быть утверждён с юристом и специалистом по информационной безопасности. Ответ: реализуем пока как есть
